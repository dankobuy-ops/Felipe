# CEO Plan: Resilient On-Demand Web Scraper

Generated by /plan-ceo-review on 2026-06-02
Branch: main | Mode: SELECTIVE EXPANSION
Repo: dankobuy-ops/Felipe

## Vision

Static SPA (GitHub Pages). Screen 1: user enters a `search_code` + `target_url`.
Submit triggers a GitHub Actions run that scrapes a highly unstable target
(crashes ~every 5 min), iterates a result list, extracts text + downloads PDFs,
stores PDFs to object storage and data to Google Sheets. Screen 2 shows results.

Core insight: a target that crashes every 5 minutes is the NORMAL operating
condition, not an exception. The architecture is defined by the crash interval.
Unit of work must be < 5 min and every unit independently retryable + resumable.

### Chosen resilience architecture (D1)
Approach A — Checkpointed self-healing on GitHub Actions. Sheets is the
checkpoint store (jobId + recordId + status, written the instant each record
finishes). On crash/timeout the workflow re-dispatches itself and resumes from
the first record not marked `done`. Idempotent on (jobId, recordId) so no record
is processed twice.

### Must-fix premise (security) — RESOLVED
The user pasting a GitHub PAT into a static SPA is a security defect. Replace
with a server-side hop that holds the credential and fires workflow_dispatch.
The SPA never sees a token.

### Locked decisions (rigor review)
- D4 — Trigger model: SINGLE-USER. PAT lives only in a backend env var /
  Actions secret; SPA gated to the owner; no public trigger surface. CAVEAT:
  a static SPA still cannot hold the PAT, so a thin server-side hop (small
  function or a local trigger script) is still required. /plan-eng-review to
  pin down where it lives.
- D5 — PDF storage: Google Cloud Storage, PRIVATE bucket, signed expiring URLs
  on Screen 2. Safe even for sensitive docs.

### Critical gaps found (must close in implementation)
1. 0-results vs page-broke discriminator: require a positive "results loaded"
   signal before accepting a 0-count, else a crash-blank page is silently
   marked done with no records. (Worst silent failure.)
2. Resume read safety: a failed/partial Sheets read must NEVER default to
   "nothing done" (would re-scrape all + risk dup writes). Fail loud + retry.
3. Re-dispatch cap: max N resumes (e.g. 10) then mark job `stalled` and show
   pending records, else a dead target loops forever burning Actions minutes.
4. No catch-all exceptions around the scrape loop (would swallow the crash
   signal we need to detect). Name every exception (see Error & Rescue Map).
5. SSRF: validate/allowlist target_url (block private IP ranges).
6. Sheets formula injection: write search_code / extracted text as strings via
   API; guard against leading `=`/`+`/`-`/`@`.
7. Sheets write-quota: batch checkpoint writes on large jobs (trades a little
   resume granularity for staying under 300 writes/min/project).

## Scope Decisions

| # | Proposal | Effort (human/CC) | Decision | Reasoning |
|---|----------|-------------------|----------|-----------|
| 1 | Live resume-progress UI on Screen 2 | ~1d / ~30m | ACCEPTED | Biggest crash-UX win; reuses checkpoint data |
| 2 | Per-record status ledger + retry failures | ~1d / ~30m | ACCEPTED | Prevents silent dropped records (prime directive) |
| 3 | Result cache by search_code | ~0.5d / ~20m | ACCEPTED | Cuts load on a target that crashes under load |
| 4 | PDF integrity verification + re-download | ~0.5d / ~20m | ACCEPTED | Corrupt/partial PDFs are likely on unstable target |
| 5 | Completion notification (email/push) | ~0.5d / ~20m | DEFERRED | Nice for long jobs; not core |
| 6 | Per-target crash-rate telemetry | ~0.5d / ~20m | DEFERRED | Operability signal; later |
| 7 | Multi-target adapter (platform) | L | DEFERRED | Turns tool into platform; future bet |

## Accepted Scope (added to this plan)
- Checkpointed self-healing scraper (Approach A) with Sheets as checkpoint store
- Server-side trigger (proxy/GitHub App) replacing browser-PAT
- Live resume-progress UI (real-time per-record progress on Screen 2)
- Per-record status ledger (done/pending/failed) with individual retry
- Result cache keyed by search_code with explicit refresh
- PDF integrity verification with re-download on corruption
